# 文档治理 — 写什么

五类文档各自的最小内容骨架，以及判断一份文档该不该存在的三判据。
守卫测试怎么写见 [GUARDS.md](GUARDS.md)。

## 五类最小内容

建立时按这个骨架起步。**宁可少写,不要铺模板**——空着的小节比填满套话的小节诚实。

### 1. 需求(最慢)

- 项目要解决什么问题;**正确定位**:它是什么、**不是**什么
- **能力边界**:能可靠回答什么 / 不能可靠回答什么(两个并列清单)
- 验收分层(能力分多层时:每层能声称什么、不能声称什么)
- 成功标准:怎么算更接近目标——**不以新增了多少字段或页面衡量**
- ✗ 不写:当前进度、已完成清单、待办

### 2. 架构(跟实现结构走)

- 分层与依赖方向(一张几行的 ASCII 图够了)
- 各层**职责边界**:**什么不许做**(`ui/` 不得直接调引擎、服务层不实现业务判断……)
- 受保护资产 / 只读目录 / 产物落地规则
- ✗ 不写:模块清单、目录树、函数说明——**这些能从代码推导,写了就是会分叉的副本**

> 判断法:一句话如果能被 `ls` 或读代码得到,就删掉;如果只有人脑里有(为什么这层不许碰那层),就留下。

### 3. 执行计划(随进度)

- 当前状态:一句话结论 + 展开
- 待启动 / 待数据工作(表:工作 · 门控在什么 · 现状)
- 已完成能力(**摘要**,逐次细节指向 git)
- 明确不做 + 每条的理由
- 显式声明**自己是状态的唯一权威**(防双权威)

### 4. handoff(随切片)

- 当前目标(当前切片是什么)
- 下一步
- 必读材料(有序,3–5 条,多了没人读)
- 验证方式(跑什么能证明没坏)
- **硬约束原文**——守卫会断言这几句在场
- 一段机器可读状态块(YAML),字段的**存在性与取值枚举**可被守卫断言(**不要断言具体取值**,见反模式 1)

### 5. ADR 索引(不衰减)

- `adr/README.md`:编号 · 标题 · 状态(accepted / superseded by NNN)· 一句话摘要
- 每条 ADR:背景 → 决策 → 后果 → 取代关系
- **已发布的 ADR 永不改写。** 要推翻就新写一条并在两边标注取代关系——改写会毁掉"当时为什么这么定"这个唯一不可替代的信息
- **别在 ADR 里写提交哈希。** 它会因 rebase / force-push 失效,而 ADR 又不许改写——两条一撞就是永远修不掉的坏引用。要指向实现就写**文件路径或函数名**

> 什么时候该新建 ADR?当一个决定**否掉了别的可行方案**、且将来有人会问"为什么不那样做"的时候。只是选了个显而易见的做法,不需要 ADR。

## 三判据

对每份文档依次过这三关。任何一关判"删",就是删。

### 判据 1 — 能不能从仓库推导出来?

**能推导 → 别写。** 代码结构、函数行为、调用关系、变更历史,读代码和 git 就有;写成文档只是制造一份会分叉的副本。

**推导不出来的只有一样:决策。** 具体说是"为什么**不**那样做"——被否掉的方案、当时的约束、拍板的理由。

> 代码告诉你"是什么",git 告诉你"怎么变的",只有文档能告诉你"为什么不那样做"。

ADR 正好全部落在这一格,所以它的每字节价值最高,应该优先写。

### 判据 2 — 衰减率

| 类型 | 衰减 | 处置 |
|---|---|---|
| **ADR / 决策记录** | **不衰减** | 永不更新,只被"取代"(supersede) |
| 需求 / 意图 | 很慢 | 长期维护 |
| 执行计划 | 任务边界 | 维护 |
| 当前状态 / handoff | **每天** | 要么勤更,**要么删掉** |
| 架构地图 | 跟代码漂 | 只有大项目才值得 |

ADR 记录的是"某时某刻的决定",代码怎么变都不影响那个事实成立——这是它不衰减的原因。

**过期的状态文档比没有更糟**:它不是缺失信息,是主动误导。宁可删。

**衰减率不同的内容不要放同一个文件。** 需求和架构合写,意味着每次架构调整都要动需求文件,既提高误改风险,也让 git 历史分不清"需求变了"还是"实现变了"。

### 判据 3 — 权威性

文档真正的功能是**成为可被争议、可被订正的共享物**。

一份从没被人读过、也没人反驳过的文档,权威性为零——它只是一份更贵的对话摘要,而且不会有人发现它错了。

**推论:没人读的文档应该删,不是留着。**
